# BMB Commercial Discovery, Enrichment and AI Scoring V1

## Scope

V1 is internal founder tooling for Liam's owner-only Commercial CRM. Its production runtime is restricted to South Africa, Johannesburg or Cape Town, and the approved Beauty/Aesthetics subsegments.

The pipeline is:

`SearchAPI discovery → public Instagram enrichment → exact client/lead dedupe → structured AI analysis → deterministic 0–10 score → P1/P2/P3 → optional Needs Approval → stop`

No step approves a lead, queues outreach, sends an email/DM, invokes Phone Farm, modifies client CT targeting, or writes to the Restaurant prospecting system.

## Providers and evidence

- Discovery reuses the existing SearchAPI Google SERP adapter and accepts only extracted Instagram profile URLs.
- Enrichment reuses the existing public Instagram profile lookup. Public contact details are retained only when directly observed in the biography.
- AI reuses OpenAI Responses with strict JSON Schema, `store: false`, a bounded timeout, sanitized inputs and an explicit prompt-injection boundary.
- Audience suggestions are other real SearchAPI candidates from the same discovery run, with profile URL, source query and extraction confidence. No audience handle is generated by the model.

External provider content is evidence, never executable instruction. Provider, JSON, schema and timeout failures fail closed and do not create a qualified lead.

## Normalized model and idempotence

`CommercialDiscoveryProvider` emits a provider identity, Instagram handle/profile URL, public search title/snippet, source query, position and extraction mode. The run ledger stores bounded counts and safe provider diagnostics. Item rows retain source, enrichment and analysis snapshots without secrets.

Before AI, the service checks active BMB clients, converted businesses, provider ID, normalized Instagram handle, website domain and normalized name plus city. A close same-city name becomes `possible_duplicate`; it is never automatically merged. The ingestion RPC repeats exact checks atomically. Run and item idempotency keys, business identifiers and existing-lead exclusion prevent replayed score events or audience snapshots.

## Score contract

`BMB_SCORING_MODEL_V1` is deterministic after structured analysis:

| Dimension | Weight |
|---|---:|
| Instagram importance | 15% |
| Content quality | 10% |
| Activity | 10% |
| Commercial strength | 10% |
| Customer value | 10% |
| Targeting fit | 15% |
| Growth potential | 10% |
| Decision-maker access | 10% |
| Budget fit | 10% |

- P1: score ≥ 8.0
- P2: score ≥ 6.5
- P3: score < 6.5
- Needs Approval: high-confidence P1, or P2 ≥ 7.2 with confidence ≥ 0.80
- Low confidence receives a deterministic penalty and cannot enter Needs Approval.

Private, missing, closed, outside-market, wrong-vertical and commercially inactive profiles are hard-rejected. Exact client, converted-business and existing-lead matches are excluded before AI. The ingestion RPC repeats these checks under lock to close races.

## Authorization and isolation

The page, API route and server service each invoke the canonical Commercial CRM owner gate. The discovery tables force RLS, expose only service-role policies and privileges, and all RPCs verify the service-role JWT claim. Generic admins, operators, support, BotApp and tenant users receive no access.

The browser never receives a Supabase service key and never calls Supabase directly.

## Canary and scale gate

The schema supports the requested future ceiling of 30 prospects per run. Production V1 is code-locked to three prospects per trigger. Increasing the runtime ceiling requires a reviewed follow-up change after inspecting:

- source validity and strict market fit;
- duplicate and existing-client exclusion;
- enrichment completeness;
- AI confidence and schema reliability;
- P1/P2 precision in Liam's actual approvals/rejections;
- provider latency, throttle and cost.

Until that review, a request above three receives `commercial_discovery_canary_limit` and no run is created.

## Runbook

1. Liam opens the owner-only Commercial dashboard.
2. Select Johannesburg or Cape Town and optionally one approved subsegment.
3. Click `Run Discovery`. The canary always processes at most three candidates.
4. Watch Queued/Running/Completed/Partial/Failed and the bounded counts.
5. Inspect every created lead's source, public snapshot, score breakdown, confidence, why-this-lead, channel, angle and sourced audiences.
6. Approve, reject or edit only through the existing Liam review workflow. Discovery itself stops.

Cost controls are a three-candidate production cap, bounded SERP pages/query count, serialized public-profile throttle, 12-second AI timeout, one transient retry and token usage persisted in the item analysis snapshot. There is no recurring cron.

## Troubleshooting

- `provider_not_configured` / `provider_key_missing`: verify canonical server environment variables; never add keys to client code.
- `provider_rate_limited`: wait for provider recovery. The run becomes partial or failed; retries are capped.
- `schema_invalid` / `invalid_json`: inspect prompt/model version and safe item error code. Do not weaken strict schema validation.
- `possible_duplicate`: compare identifiers manually. Do not force a merge from the Discovery UI.
- empty Needs Approval with created leads: P3 and lower P2 are intentionally stored outside Liam's default queue.
- stuck queued/running: inspect Vercel function logs using the run ID; do not manually mark leads approved or queue outreach.

## Rollback

The rollback is intentionally fail-closed. It refuses to remove the feature while any discovery run, item, identifier or V1-scored lead exists. Runtime records must first be reviewed and handled explicitly; the rollback never silently deletes commercial evidence.
